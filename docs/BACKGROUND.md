# 背景 · 俱乐部为什么会垮，工具能帮什么

> 消化自「例会台产品蓝图」。例会台是一个相关的独立项目，由伙伴交接过来。这里只留下和 EOE Club OS 运营有关的部分；蓝图里关于商业化、小程序主体、合作分工的内容不放在这里。

## 一个循环

人少 → 同一批人扛角色和官员 → 累了 → 例会不完整（没有备稿 / 没有点评）→ 来宾不回来 → 续费的人不够 → 俱乐部暂停。

工具只能打断其中「事务」的几环：让空缺早点暴露，让交接不靠某个人的记忆，让来宾会后有人联系，让表彰有据可依。氛围、冲突、点评的分寸、有没有人愿意当官员，这些是人的事，工具最多给个提醒。

**设计原则：少占官员的时间，多给他们可以拿去和人相处的时间。**

## 两个项目怎么分工

| | EOE Club OS（本仓库） | 例会台（独立项目） |
|---|---|---|
| 管什么 | 入口和经验沉淀：成长百科、官员工作台、会后记录、看板 | 一场例会的执行：模板 → 接龙 → 会单 → 现场即兴白板 → 投票 → 归档 |
| 核心想法 | 已有工具能解决的不重复做，只放链接和说明 | 会单即记录：一张会单贯穿整场，会后它就是这场的档案 |

**不合并。** Club OS 的原则是不自建接龙和投票，而这正是例会台的主业，两边各自保持简单。等例会台真正可用、有了长期链接，在 `content/tools.yaml` 的「例会协作」里加一条入口就行，不用改代码。

## Club OS 吸收了什么

只吸收能马上减轻运营负担、又不增加录入的部分：

- **空缺早暴露**：「下一场例会」里填了角色、名字还空着的，首页和例会页直接显示「还缺 N 个角色」。
- **会单即记录（轻量版）**：会后记录自动带出刚开完那场例会的日期和主题（原来就有）。
- **衰退信号**：主席工作台每月看一眼——角色是不是总落在同一批人身上、有没有缺备稿或缺点评、来宾有没有人联系、官员是不是累了。只是自查提醒，不做自动预警。
- **交接不断档**：网站和数据库至少两位官员能管理（主席工作台 · 本届任期）。

来宾跟进、新人第一个角色、换届交接，成长百科和官员工作台里已经有了，不重复。

## 没吸收的

以后要做，得先有真实摩擦，记在 [BACKLOG.md](BACKLOG.md)：

- **来宾 48 小时跟进提醒**：涉及个人信息，要先定隐私规则，即只记最少字段、只有 VPM 能看、到期自动删除。
- **角色历史、公平轮换、Pathways 必做角色核对**：需要按人记录每场角色，这是例会台的数据。
- **健康度自动预警**：先靠人看看板。

## 两条红线

1. 「Toastmasters / 头马」是头马国际的商标。对外的产品不叫「头马 xx」，也不暗示官方身份。
2. EOE 的会员记录、海报、人物照片只属于 EOE，不拿去做别的项目的演示素材。每个俱乐部的数据只属于它自己。
